# Metasys sign-in — 1.2.2 production-test candidate

Profile validation first requests private v6 userinfo. Only HTTP 404 triggers a private v5 userinfo request on the same verified HTTPS server, supporting the profile contract confirmed by the Metasys 13 diagnostic. Invalid profiles, rejected credentials and certificate errors fail closed. The same validation applies during session refresh; login credentials are never retried to select a profile version.

Point Bridge is installed on the Metasys server. The installer requires the local MIIIDM core service. Older Metasys UI versions do not need the newer UI Assets registry entry. First-run setup verifies your Metasys login against the local UI, then enables sign-in for all valid Metasys users. Each receives Point Bridge Administrator access. Disabled, locked, expired and substituted identities are rejected. A failed Metasys login never silently falls back to local authentication. Passing installation detection does not establish authentication compatibility with an older Metasys version.

On a fresh installation, open http://127.0.0.1:5088/ on that server. Enter the code from C:\ProgramData\MetasysPointBridge\setup-code.txt, the trusted HTTPS address of Metasys on this computer, and your Metasys username/password. Select Verify Metasys and complete setup, then sign in. No separate local account or JSON editing is required. Source/destination API credentials remain separate.

For an existing installation, sign in with the local account. Metasys setup opens automatically when unconfigured and remains available under User accounts → Configure Metasys sign-in. Save the local HTTPS address, verify a Metasys login, then enable sign-in. Changes apply without restarting. Changing servers clears verification and disables sign-in until verified again. The address must resolve to this computer and pass normal HTTPS certificate validation. Passwords are never saved. Settings are saved atomically in the restricted ProgramData metasys-login.json, which overrides legacy websettings.json login configuration. Existing explicit grants remain supported until changed in setup. Create a local recovery administrator under User accounts if needed; use the Local recovery sign-in link for maintenance. Metasys-only first setup does not create a duplicate local password account.

The adapter uses the private Metasys UI JSON challenge/login, canonical /userinfo, refresh and logout contract observed on the metasys-lab Metasys16 lab. This is not a claimed supported public vendor authentication API. Other versions and service-account TLS context must be verified on the target server. Explicit disabled/locked/expired status is denied; an absent optional status is unknown. Refresh success alone does not establish every account policy. Terms acceptance is handled by the user through the normal Metasys UI.

Passwords are used for the login operation and are not saved by this provider. Remote tokens live only in bounded server-side memory sessions; browser cookies contain no vendor token. Canonical identity and configured origin/grant binding are revalidated. Provider failures revoke external sessions rather than silently granting access. Logout removes the local session and attempts remote cleanup.

Default deployment is normal paused operation, not the lab-only Acceptance mode. Do not copy lab websettings.json, credential files, encryption keys or acceptance directories to a customer server. See INSTALL-AND-REMOVE.md and RECOVERY-AND-DIAGNOSTICS.md.
