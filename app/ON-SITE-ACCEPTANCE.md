# Local deployment acceptance and rollback

All customer checks are performed on site by the operator. No customer network access or credentials should be sent to the development session.

1. Preflight: record Windows edition/build, architecture and Metasys version locally; verify they meet the selected .NET10 and Metasys deployment requirements. Validate the actual HTTPS authentication origin and certificate chain without trust bypasses. Verify package SHA256 against the release manifest and apply the organization's signing/release process. Back up the existing application and service data with its original ACLs. Record service identity, paths and bindings. The bundled runtime must remain separate from Metasys-installed runtimes.
2. Keep the original application and transfer configuration backed up. Use an isolated loopback-only data directory and Acceptance.LoginOnly=true for login acceptance. This flag omits the transfer worker and blocks non-authentication writes even for an Administrator. Do not put the acceptance flag in the normal deployment inadvertently; do not reuse live API mappings or service credentials for this test.
3. Configure the approved authentication server and exact canonical user grants locally. Every configured user receives Administrator access. Confirm the user is intended to manage connection credentials, accounts, mappings and transfers. Do not grant automatic access to every server user. No lab grants ship in this package. If canonical identity is unknown, establish it through a locally entered one-login/identity/refresh/logout test before creating the grant; never guess IDs or transfer passwords to chat.
4. Login-only acceptance: enter the existing user's password locally, confirm one-form sign-in and correct canonical username/Administrator badge, refresh, sign out, and confirm protected pages are unavailable. Verify transfers remain paused and source/destination are unconfigured. Do not accept legal terms automatically; users handle terms through normal Metasys UI.
5. With a disposable account and separate approval, test disabled/locked/expired status, password changes and login-time restrictions against both new logins and existing sessions; record revocation timing locally. Refresh success alone does not prove every policy. Test provider outage and identity/grant changes. Do not repeatedly test production accounts or trigger avoidable lockouts.
6. Before actual operation, independently test source/destination API versions, credentials and point-specific permissions using Admin / Connections. Authentication acceptance does not establish API or transfer compatibility. Keep writes paused until point types, units, destination semantics and rollback are validated under explicit operational approval.
7. Rollback: stop only the new app/service under the local change process, restore the backed-up application/configuration/data and original ACLs/service bindings, and start the prior version with transfers paused. Recheck local administrator maintenance access and API connectivity. External sessions are memory-only and invalidated by restart; review remote session cleanup through normal Metasys administration if logout could not be confirmed. Preserve the original backup until acceptance is complete.


This checklist is a procedure, not authorization to access a customer network, deploy, create accounts or activate transfers.

For a separate API-authentication acceptance phase, retain Acceptance.LoginOnly=true and explicitly set Acceptance.AllowConnectionTests=true. Only API save/test/clear routes are then allowed in addition to authentication. Transfer worker remains absent and transfer/mapping mutations remain blocked. Enter API credentials locally and click Test connection; this does not save settings. Confirm Save connection persistence separately without starting transfers. Return the flag to false for strict login-only testing. Shipping defaults do not enable either acceptance mode or Metasys login.
